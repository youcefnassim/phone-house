## Target SQL permissions

The standalone review-only `legacy/db/security/REVIEW06_PERMISSION_DESIGN.sql` demonstrates self-bound role checks, locked search paths and table/function grants. It is NOT a seventh approved migration. It revokes broad authenticated DML, does not implement command RPCs and must not be applied independently. Review all object owners and inherited grants in `pg_roles`, `pg_auth_members`, `pg_namespace`, `pg_class`, `pg_proc` and `pg_default_acl` before enabling API schemas.

Each new public table must have explicit same-migration GRANTs before RLS/policies. Business writes are command-only: authenticated receives SELECT only on approved cost-free projections/tables, not INSERT/UPDATE/DELETE on financial or stock tables. `anon` receives neither operational table access nor function EXECUTE. `service_role` bypasses RLS: reserve it for explicit provisioning/maintenance, never ordinary reads or deciding caller role.

Prefer invoker reads with RLS. Privileged command functions must use a controlled non-login owner with only necessary object permissions, `SET search_path = pg_catalog`, schema-qualified identifiers, no uncontrolled dynamic SQL, identity/role/store checks at entry, and narrowly granted EXECUTE. Revoke PostgreSQL's default PUBLIC EXECUTE on every created function. Set default privileges FOR EACH actual migration/function creator; one ALTER DEFAULT PRIVILEGES does not cover other owners. Runtime API roles must not have CREATE in public or be function owners. RLS cannot constrain a bypass role or table owner by itself.

Owner financial read uses `auth.uid()` internally and a database Super Admin check; return explicit decimal-text columns only. No operational table join, audit JSON, replay response, log, export or browser bundle may contain owner costs. Current synthetic owner bundle is not a security boundary: exclude all confidential fixtures and demo finance modules from an activated production graph. Audit has operational allowlisted details separate from owner-only finance audit. Null-store audit events are not globally readable. Cash expected totals require a distinct protected projection, not a normal Seller cash-row read.

## Provisioning and sessions (design only)

No auth code, account creation or config change is performed. Profiles are required for display identity; roles remain in `user_roles`, never profiles. Future profile creation trigger uses sanitized display data and grants no role/membership. Self-registration is disabled for operational access; any external Auth account without explicit provisioning has no operational rights. Auth provider selection and profile fields must be confirmed before implementing authentication.

First Super Admin bootstrap requires owner approval of the dedicated project reference and exact Auth UUID. Owner creates/verifies the Auth user through the dedicated project's Auth administration; do not accept an email-derived lookup or signup metadata as role proof. In a reviewed transaction, lock bootstrap state, ensure no existing owner (otherwise use normal audited administration), insert the profile if absent, assign SUPER_ADMIN and approved memberships, and write a restricted immutable provisioning audit. Use an explicitly authorized temporary privileged administrative connection; remove temporary access afterward. Re-runs must not promote another user. Never bundle bootstrap in app startup, migration fixtures or a public endpoint. Record operator/project/UUID/time/reason without credentials.

Operational provisioning similarly requires an authenticated existing Super Admin, explicit role/store assignments, uniqueness, audit, and no privilege self-promotion path. Destructive role changes require last-owner protection and revocation review. Session expiry, inactivity window and device policy remain unconfigured pending owner/OD-18; do not invent durations. Reject expired JWT; validate getUser; inspect disabled provisioning and current memberships each command. Revoke refresh sessions on role removal/device loss; invalidate identity-scoped caches on signout/switch, without refetching protected queries on signout.

M01 seller handoff must reauthenticate the incoming approved seller, verify M01 membership and active terminal/shift, then atomically record prior actor/new actor/terminal/shift/time/reason. Selected sellerId alone never changes authenticated attribution. No session secrets in audit. M02 never inherits M01 shared-terminal assumptions (OD-04). Handoff/session timing and offline identity rules require approval before activation.
